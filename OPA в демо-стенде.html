    Как OPA устроена в демо-стенде

    OPA — это движок сравнения двух бирок: tenant_id пользователя и tenant_id ресурса. Он не хранит данные, не проксирует запросы и не говорит ни с одной из систем напрямую. Всё, что он делает, — отвечает «да» или «нет» на один HTTP-запрос. Этот справочник показывает, кто и как его об этом спрашивает в каждой из пяти точек интеграции.

    Движок

    authz.rego — один файл политики на всех

    OPA — универсальный исполнитель правил; authz.rego — это ваши конкретные правила. Он не знает, что такое Airflow или Superset — видит только JSON {user, action, resource} и сравнивает поля.

    rbac_allow

    Есть ли у роли пользователя разрешение на это действие в role_permissions. Проверка «по роли», не по тенанту.

    same_tenant

    input.user.tenant_id == input.resource.tenant_id. Тривиальное сравнение строк — не знает, откуда они взялись.

    // authz.rego — упрощённо
rbac_allow {
    some role in input.user.roles
    input.action in role_permissions[role][input.resource.type]
}

same_tenant {
    input.user.tenant_id == input.resource.tenant_id
}

allow { rbac_allow; same_tenant }

// сервисные роли (metadata_ingestion, bi_admin) обходят same_tenant —
// им по определению нужен обзор по обоим тенантам сразу
allow { rbac_allow_service }
    Ключевой момент: содержательная разница между пятью случаями ниже — не в authz.rego, а в том, что именно каждый вызывающий код подставляет в resource.tenant_id перед отправкой запроса.

    Точка интеграции № 1

    Postgres — через Gateway live, на каждый запрос проверка тривиальна

    demo-api/main.py

    resource.tenant_id = user["tenant_id"] — ресурс помечен тем же тенантом, что и сам пользователь. same_tenant тут всегда true. Реальная защита строк — Postgres RLS, OPA лишь проверяет право роли на действие.

    01

    Браузер → main.py

    Запрос GET /sales. Gateway игнорирует любой tenant_id из параметров — берёт его только из JWT.

    02

    main.py → OPA

    check_opa(user, "read", {"type":"sales_data", "tenant_id": user.tenant_id})

    03

    main.py → Postgres

    Если allow — Gateway сам выполняет SET app.tenant_id и SQL-запрос через своё psycopg2-подключение. RLS фильтрует строки.

    Точка интеграции № 2

    Airflow — DAG'и live, на каждый запрос настоящая проверка

    airflow-custom/opa_auth_manager.py · класс OpaFabAuthManager, встроен в процесс Airflow

    resource.tenant_id = _dag_tenant(dag_id) — парсится из префикса <tenant_id>__ в имени самого DAG'а, независимо от того, кто спрашивает. Здесь same_tenant действительно что-то решает.

    01

    Клик «открыть DAG»

    Airflow webserver сам вызывает свой метод is_authorized_dag().

    02

    OpaFabAuthManager → OPA

    tenant_id ресурса — из имени DAG'а (company_a__load_dataset → company_a), не из юзера.

    03

    Обратно в Airflow

    Если allow — управление возвращается в сам Airflow, он рендерит DAG как обычно, из своей метаданных-БД.

    Точка интеграции № 3

    Superset — дашборды live, на каждый запрос настоящая проверка

    superset-custom/opa_security_manager.py · класс OpaSupersetSecurityManager, встроен в процесс Superset

    resource.tenant_id = _tenant_from_name(name) — префикс из названия дашборда/датасета. Для датасетов есть запасной путь: если префикса в имени нет (UI не даёт переименовать физический датасет), тенант берётся из названия Database-подключения через DB_NAME_TENANT_MAP.

    01

    Открытие дашборда

    Superset сам вызывает can_access_dashboard() / raise_for_access().

    02

    OpaSupersetSecurityManager → OPA

    Сравнивает tenant_id из имени дашборда с tenant_id пользователя (из LDAP-группы).

    03

    Обратно в Superset

    Если allow — Superset выполняет SQL через своё Database-подключение (под tenant-scoped ролью Postgres) и рисует график.

    Известное ограничение: списки Charts (и отчасти Dashboards) не фильтруются этой проверкой на уровне списка — названия обоих тенантов видны всем. Реальные данные при открытии всё равно блокируются OPA — утекают только заголовки.

    Точка интеграции № 4

    MinIO — объекты в бакете офлайн, заранее проверка тривиальна

    minio-sync/sync_minio_policies.py · отдельный скрипт, не часть MinIO

    Единственный случай, где OPA не стоит на пути реального запроса. Скрипт заранее приводит IAM-политики MinIO в соответствие с ответами OPA; в момент самого обращения к файлам OPA уже не участвует.

    01

    Заранее: sync → OPA

    Для каждой LDAP-группы: resource.tenant_id = tenant_id (= tenant_id юзера, тривиально).

    02

    sync → MinIO (API)

    Если allow — скрипт сам вызывает mc idp ldap policy attach/detach, меняя конфигурацию MinIO.

    03

    Позже: DAG → MinIO напрямую

    AssumeRoleWithLDAPIdentity + GetObject. MinIO проверяет свою же, заранее привязанную политику. OPA не спрашивается.

    Следствие: если поменять authz.rego и не перезапустить docker compose run --rm minio-sync — MinIO продолжит жить по старым правилам сколько угодно долго.

    Точка интеграции № 5 — другая роль

    ClickHouse — журнал решений, не защищаемый ресурс

    clickhouse-init/01-audit-log.sql · 02-request-log.sql

    ClickHouse не хранит бизнес-данные, которые нужно делить по тенантам. Это общий приёмник: все четыре источника выше пишут сюда результат своего обращения к OPA — после того, как получили ответ, а не вместо запроса к OPA.

    ТаблицаЧто в нейКто пишет
    audit.audit_logКаждое решение OPA: user, action, resource, allow, deny_reasonmain.py, opa_auth_manager.py, opa_security_manager.py, sync_minio_policies.py
    audit.request_logСырой HTTP-лог Gateway — включая запросы, которые до OPA не дошли (напр. 401 по JWT)demo-api/main.py
    Не подтверждено: в authz.rego есть право "audit_log": {"view_audit_log"} (только у admin) — то есть чтение журнала задумано как ещё одно действие, требующее проверки OPA. Но код, который бы реально делал этот запрос при чтении ClickHouse, пока не найден среди присланных файлов — либо не реализован, либо не был показан.
