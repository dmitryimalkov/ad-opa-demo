# Сценарий демонстрации: AD + Keycloak + OPA + Postgres RLS + Airflow + MinIO

Полный сквозной путь — от логина до всех пяти путей изоляции, которые
есть на стенде. **Ядро (шаги 1-8)** — 18-23 минуты, самое важное для
любой аудитории. **Расширение (шаги 9-10)** — ещё 15-18 минут,
показывает, что тот же принцип работает и для оркестрации (Airflow),
и для S3 (MinIO). Если время ограничено — можно показать только ядро
и рассказать про Airflow/MinIO словами (раздел "Куда это ведёт
дальше" в конце).

Каждый шаг: команда → что должно произойти → что это доказывает.
Идите по порядку — каждый следующий шаг опирается на то, что уже
увидели.

## 0. Перед началом

- Терминал открыт, SSH-сессия на VM активна.
- Браузер открыт на `http://192.144.13.138:8080` (phpldapadmin) —
  понадобится в шаге 1.
- Заранее выполните `docker compose ps` — покажите, что весь стенд
  состоит из отдельных контейнеров (LDAP, Keycloak, OPA, Postgres,
  Airflow, MinIO, Gateway) — это не "одна программа", а несколько
  независимых систем.
- Если время поджимает — прогоните `./preflight-check.sh` заранее,
  до прихода аудитории, а не во время показа.

# ЯДРО (18-23 минуты)

## 1. Структура данных (2 минуты)

Откройте phpldapadmin, разверните `ou=people` и `ou=groups`.

**Тезис:** "Это наш AD-совместимый каталог. Alice и Bob — сотрудники
Company A, Carol и Dave — Company B. Вся информация о том, кто есть
кто, живёт здесь, а не в нашем коде."

## 2. Логин и что видит Gateway (3 минуты)

```bash
TOKEN_ALICE=$(curl -s -X POST "http://localhost:8081/realms/demo/protocol/openid-connect/token" -d "client_id=demo-gateway" -d "grant_type=password" -d "username=alice" -d "password=Password123!" | jq -r .access_token)

curl -s http://localhost:8000/whoami -H "Authorization: Bearer $TOKEN_ALICE" | jq
```

**Ожидаемо:** `tenant_id: company_a`, `roles: ["analyst"]`.

**Тезис:** "Alice вошла своим паролем из LDAP. Keycloak превратил её
членство в группе `CompanyA-Analysts` в подписанный токен. Gateway
разобрал из токена и компанию, и роль — нигде в коде нет строчки
`if username == "alice"`."

## 3. Изоляция данных — работает (2 минуты)

```bash
curl -s http://localhost:8000/sales -H "Authorization: Bearer $TOKEN_ALICE" | jq
```

**Ожидаемо:** только строки `company_a`.

## 4. Главный "вау-момент" — попытка подмены (2 минуты)

```bash
curl -s "http://localhost:8000/sales?tenant_id=company_b" -H "Authorization: Bearer $TOKEN_ALICE" | jq
```

**Ожидаемо:** всё равно только `company_a`, обратите внимание на поле
`note_ignored_query_param`.

**Тезис:** "Я специально оставил в API параметр, который ничего не
делает — это провокация. Даже если бы кто-то в коде случайно начал
его использовать, Postgres всё равно не отдал бы чужие строки —
это будет видно в следующем шаге."

## 5. Отказ по роли (2 минуты)

```bash
TOKEN_DAVE=$(curl -s -X POST "http://localhost:8081/realms/demo/protocol/openid-connect/token" -d "client_id=demo-gateway" -d "grant_type=password" -d "username=dave" -d "password=Password123!" | jq -r .access_token)

curl -s http://localhost:8000/sales -H "Authorization: Bearer $TOKEN_DAVE" | jq
```

**Ожидаемо:** `403`, `deny_reason: ["role_not_permitted"]`.

**Тезис:** "Dave — viewer, ему не положено читать сырые данные. Причём
отказ содержит явную причину — это для аудита и для UX, а не просто
глухой 403."

## 6. Автоматические тесты изоляции (2 минуты) — самый убедительный аргумент для инженеров

```bash
docker exec -it demo-opa opa test /policies -v
```

**Тезис:** "Это не 'мы вроде проверили руками' — это тесты, которые
гоняются в CI при каждом изменении политики. Если кто-то случайно
ослабит правило и Company A получит доступ к Company B — тест
`test_analyst_cannot_read_other_tenant` упадёт немедленно."

*Опционально, для эффекта:* откройте `authz.rego`, ослабьте условие
`same_tenant` прямо на глазах у команды, перезапустите `opa test` —
покажите красный `FAIL`. Верните файл обратно.

**Важно для себя (не для аудитории):** если правите `authz.rego`
вживую — **следите за кавычками у строк** (`{"s3_access"}`, а не
`{s3_access}`). Без кавычек OPA не скомпилирует файл и молча
останется на предыдущей рабочей версии — снаружи это выглядит так,
будто правка "не подействовала", хотя на самом деле она просто не
применилась. Проверить: `docker logs demo-opa --tail 5`, смотреть на
`err`.

## 6.5. Аудит-лог — кто и когда получал доступ (3 минуты)

**Тезис перед показом:** "Всё, что мы только что делали — логин Alice,
чтение `/sales`, отказ Dave'у — уже записано. Не в логах контейнера,
которые исчезнут при перезапуске, а в отдельной таблице ClickHouse,
специально под это. Покажу двумя способами — как видит обычный
пользователь и как видит вся картина целиком."

Получите токен под Bob (admin, Company A):
```bash
TOKEN_BOB=$(curl -s -X POST "http://localhost:8081/realms/demo/protocol/openid-connect/token" -d "client_id=demo-gateway" -d "grant_type=password" -d "username=bob" -d "password=Password123!" | jq -r .access_token)

curl -s http://localhost:8000/audit-log -H "Authorization: Bearer $TOKEN_BOB" | jq
```

**Ожидаемо:** список записей — но **только** по `company_a`, включая
Alice, но не Carol/Dave.

**Тезис:** "Это тот же принцип tenant-изоляции, применённый рекурсивно
— даже сам аудит-лог не показывает Bob'у чужую компанию, хотя он
admin. И заметьте — Alice (analyst) вообще не может открыть этот
эндпоинт:"

```bash
curl -s http://localhost:8000/audit-log -H "Authorization: Bearer $TOKEN_ALICE" | jq
```
**Ожидаемо:** `403`.

Теперь покажите "вид с высоты птичьего полёта" — без tenant-фильтра,
напрямую из ClickHouse (это то, что видит **только** оператор
платформы, никогда не пользователь):
```bash
docker exec -it demo-clickhouse clickhouse-client --password <ваш_пароль_clickhouse> -d audit -q "SELECT ts, user_sub, user_tenant_id, action, allow, deny_reason FROM audit_log ORDER BY ts DESC LIMIT 15 FORMAT PrettyCompact"
```

**Тезис:** "Здесь видно вообще всё — и company_a, и company_b, и все
отказы с причинами. Это уже не API с фильтром по tenant, а прямой
доступ к самой базе аудита — то, что должно быть максимально
ограничено на практике, ровно как мы обсуждали с суперпользователем
Postgres в следующем шаге."

## 7. Прямой доступ к БД — другой путь изоляции (4 минуты)

Откройте `http://192.144.13.138:8000/portal` в браузере. Введите
`alice`/`Password123!` → **Получить доступ к БД**.

**Ожидаемо:** host/port/username/password + `valid_until` (+15 минут
от текущего момента).

**Тезис:** "Это другой путь — DBeaver говорит с Postgres не по HTTP,
а по SQL-протоколу, где нет места вставить OPA на каждый запрос.
Поэтому OPA проверяется один раз — здесь, при выдаче пароля. Дальше
изоляцию держит не Gateway, а сам Postgres, через роль подключения."

Подключитесь этими credentials в DBeaver, выполните
`SELECT * FROM sales` — покажите, что видно только `company_a`, без
единого `WHERE`.

**Дополнительный тезис про TTL:** "Пароль живёт ровно столько же,
сколько и JWT — 15 минут, задано на уровне самого Postgres через
`VALID UNTIL`. Не нужен отдельный cron, который бы отзывал старые
пароли — база сама откажет в подключении по истечении времени."

## 8. Что если убрать RLS совсем (2 минуты, опционально, для эффекта)

```bash
docker exec -it demo-postgres psql -U postgres -d salesdb -c "SELECT * FROM sales;"
```

**Ожидаемо:** видны строки ОБЕИХ компаний.

**Тезис:** "Это суперпользователь — RLS на него не действует по
определению. Поэтому в реальном проде супер-права должны быть
максимально ограничены и никогда не использоваться для повседневных
подключений приложения."

# РАСШИРЕНИЕ (15-18 минут) — Airflow и MinIO

Тезис перед началом расширения: "Всё, что вы видели — либо HTTP через
Gateway (OPA на каждый запрос), либо прямой доступ к БД (OPA один раз,
дальше RLS). Дальше — ещё два случая: Airflow, тоже HTTP-приложение
(значит, OPA снова можно спрашивать на каждое действие), и MinIO —
снова 'сырой' протокол, как Postgres, но с другим механизмом
изоляции."

## 9. Airflow — мультитенантные датасеты и метаданные (8 минут)

### 9.1. Alice — видит только своё (2 минуты)

Откройте `http://192.144.13.138:8090`, войдите `alice`/`Password123!`.
Откройте вкладку **Dag-и**.

**Ожидаемо:** ровно один DAG — `company_a__load_dataset`.

**Тезис:** "Alice вошла собственным LDAP-паролем — не через Keycloak,
не через наш Gateway. Список DAG сформировала сама живая проверка
внутри Airflow: он спросил у LDAP, в каких Alice группах, и спросил у
того же самого OPA, что использует Gateway — можно ли ей видеть этот
DAG."

### 9.2. Carol — контраст (2 минуты)

Разлогиньтесь, войдите `carol`/`Password123!`.

**Ожидаемо:** ровно один DAG — `company_b__load_dataset`, причём
**не** видно `company_a__load_dataset`.

**Тезис:** "Тот же интерфейс, тот же код — но Carol физически не
видит даже название чужого DAG. Изоляция не 'запрещено открывать', а
'не существует' с её точки зрения."

### 9.3. Dave — отказ по роли (2 минуты)

Разлогиньтесь, войдите `dave`/`Password123!`. Откройте вкладку
**Dag-и** (не главную страницу — там у viewer отдельно показывается
`403` на виджетах статистики, это особенность UI Airflow, не связанная
с нашей логикой).

**Ожидаемо:** `0 Dags`.

**Тезис:** "Dave состоит в компании B, как и Carol, но у него роль
viewer — по нашей матрице ролей viewer вообще не имеет доступа к
датасетам."

### 9.4. Живой код вместо магии (2 минуты, для инженерной аудитории)

```bash
docker exec demo-airflow python3 -c "
import ldap
conn = ldap.initialize('ldap://ldap:389')
conn.simple_bind_s('cn=admin,dc=demo,dc=local', 'AdminPass123!')
print(conn.search_s('ou=groups,dc=demo,dc=local', ldap.SCOPE_SUBTREE, '(member=uid=carol,ou=people,dc=demo,dc=local)', ['cn']))
"
```

**Тезис:** "Вот буквально то, что Airflow делает при каждом открытии
списка DAG — обычный LDAP-запрос, тот же самый, что мы весь месяц
делали руками через `ldapsearch`."

## 10. MinIO — S3 через нативный LDAP (7-10 минут)

### 10.1. Alice получает доступ своим LDAP-паролем (2 минуты)

```bash
docker exec -i demo-api python3 /dev/stdin alice Password123! < minio-init/minio_full_test.py
```

**Ожидаемо:**
```
Успех — временные credentials для alice получены (STS).

--- Пытаемся прочитать company_a/ ---
  Доступно, объектов: 0 []
--- Пытаемся прочитать company_b/ ---
  ОТКАЗАНО: AccessDenied — Access Denied.
```

**Тезис:** "Alice представилась своим LDAP-паролем напрямую в MinIO —
ни Keycloak, ни наш Gateway тут вообще не участвовали. MinIO сам
сходил в LDAP, нашёл её группу, выдал временный ключ, ограниченный её
же префиксом."

### 10.2. Carol — зеркально (1 минута)

```bash
docker exec -i demo-api python3 /dev/stdin carol Password123! < minio-init/minio_full_test.py
```

**Ожидаемо:** `company_b/` доступен, `company_a/` — отказ.

### 10.3. Dave — самый интересный момент (2 минуты)

```bash
docker exec -i demo-api python3 /dev/stdin dave Password123! < minio-init/minio_full_test.py
```

**Ожидаемо:**
```
ОШИБКА STS: 400 ...InvalidParameterValue...
expecting a policy to be set for user...
```

**Тезис:** "Обратите внимание — Dave не получил отказ при попытке
*прочитать* данные. Ему отказали ещё на этапе *входа*. У него и его
группы нет ни одной привязанной IAM-политики, и MinIO в принципе не
выдаёт временный ключ человеку, для которого заведомо нет ни одного
разрешённого действия. Это строже, чем в Postgres, где 'зайти можно,
толку ноль' — здесь даже 'зайти' не получится."

### 10.4. Тестирование политик MinIO вживую — доказываем, что связь с OPA настоящая (4-5 минут)

Это самый содержательный момент для инженерной аудитории — живой
эксперимент "сломать → доказать → починить → доказать снова",
показывающий, что привязка IAM-политик в MinIO не хардкод, а реально
управляется через `authz.rego`.

**Шаг 1 — временно уберите доступ у analyst.**
Откройте `opa-policies/authz.rego`, в блоке `"analyst": {` замените:
```rego
"s3_bucket": {"s3_access"},
```
на:
```rego
"s3_bucket": set(),
```
Сохраните. Подождите 5 секунд — OPA сам перечитает файл (`--watch`).

**Проверка, что OPA принял файл** (важно — если забыть кавычки вокруг
`"s3_access"`, компиляция упадёт и OPA молча останется на старой
версии):
```bash
docker logs demo-opa --tail 3
```
Не должно быть `err` в последних строках.

**Шаг 2 — запустите синхронизацию заново:**
```bash
docker compose run --rm minio-sync
```

**Ожидаемо:**
```
[minio-sync] CompanyA-Analysts: OPA deny, политика привязана -> ОТВЯЗЫВАЮ company-a-policy
[minio-sync] CompanyB-Analysts: OPA deny, политика привязана -> ОТВЯЗЫВАЮ company-b-policy
```

**Шаг 3 — проверьте на Alice:**
```bash
docker exec -i demo-api python3 /dev/stdin alice Password123! < minio-init/minio_full_test.py
```
**Ожидаемо:** та же ошибка `InvalidParameterValue`, что раньше была
только у Dave — Alice (analyst) больше не проходит.

**Тезис:** "Мы только что поменяли одну строчку в файле политики — и
это изменение реально дошло до MinIO, через OPA и `minio-sync`. Это
не имитация и не хардкод — настоящая, проверяемая связь."

**Шаг 4 — верните всё обратно**, повторите шаги 1-2 в обратную
сторону, и снова проверьте Alice — доступ должен вернуться.

**Честная оговорка, обязательно проговорить:** "Это не live-канал,
как у Gateway/Airflow. `authz.rego` и MinIO совпадают только на
момент запуска `minio-sync` — запускать нужно вручную после каждой
правки политики. Сам MinIO перезапускать не нужно — привязки
применяются мгновенно через API, просто применяет их именно этот
скрипт, а не что-то, что следит за файлом само."

### 10.5. Показать сам связующий код (2 минуты, опционально)

Откройте `minio-sync/sync_minio_policies.py`, покажите функции
`fetch_all_groups`, `check_opa`, `attach_policy`/`detach_policy`.

**Тезис:** "Тот же паттерн `check_opa`, что в Gateway и в
`opa_auth_manager.py` Airflow — переиспользуем идею, а не изобретаем
заново для каждого нового компонента."

## 11. Куда это ведёт дальше (2-3 минуты, без демонстрации — только рассказ)

- **Много AD у разных клиентов** — вместо прямой LDAP-федерации
  используется Identity Brokering (Keycloak как посредник между
  вашей платформой и SSO каждой компании) — LDAP-федерация, которую
  вы видели в шаге 1, подходит только когда AD один.
- **ClickHouse как полноценное хранилище датасетов** — сейчас
  ClickHouse в стенде используется только для аудит-лога. Тот же
  паттерн, что и MinIO (нативная LDAP-авторизация с Role Mapping +
  свой `clickhouse-sync`), можно повторить, если понадобится хранить
  там сами данные, а не только логи.
- **Аудит для Airflow и MinIO** — сейчас в ClickHouse попадают только
  решения OPA от Gateway. Решения `opa_auth_manager.py` (Airflow) и
  `minio-sync` пока логируются только в stdout контейнеров — логичное
  развитие: писать и их в тот же `audit.audit_log`.

## Частые вопросы от аудитории (подготовленные ответы)

**"А что если Gateway упадёт?"** — прямой доступ к БД и S3 продолжит
работать (они не зависят от Gateway в момент самого запроса), но
новые пароли/URL выдавать станет некому, пока Gateway не поднимется.

**"Почему не всё через OPA?"** — потому что OPA физически не может
встроиться в бинарные протоколы (SQL, S3) на каждый запрос без
дорогого прокси-слоя. Вместо этого OPA проверяется в момент выдачи
"пропуска" или, как у MinIO, при периодической синхронизации, а
дальше барьер держит нативный механизм (RLS, IAM-политика).

**"Что мешает Alice скопировать пароль/токен и отдать его Bob?"** —
на уровне самого секрета ничего не мешает; но каждая выдача (шаг 6.5)
попадает в аудит-лог с точным временем и tenant'ом, а короткий TTL
(15 минут у Postgres-credentials, 1 час у MinIO STS по умолчанию)
ограничивает окно, в течение которого скопированный секрет вообще
актуален.

**"Почему Airflow и MinIO логинятся напрямую, а не через ваш
Gateway/портал?"** — оба поддерживают нативную LDAP-авторизацию
из коробки (у Airflow — через Flask-AppBuilder, у MinIO — через
встроенный STS `AssumeRoleWithLDAPIdentity`). Раз механизм уже есть
и хорошо документирован — переиспользуем его, вместо того чтобы
городить ещё один слой поверх.

**"Почему MinIO-sync не автоматический?"** — потому что у нас нет
события "authz.rego изменился" в реальном времени для внешних
скриптов (в отличие от самого OPA, у которого есть `--watch`).
Можно было бы добавить, например, файловый watcher или git-хук,
который сам запускает `minio-sync` при коммите изменений в
политику — это осознанно оставлено как следующий шаг, не сделано
специально.
