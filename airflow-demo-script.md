# Сценарий демонстрации: мультитенантный Airflow через OPA

Продолжение основного `demo-script.md` — отдельный блок минут на 10-12,
показывающий, что тот же принцип (OPA как judge, а не enforcer) работает
не только для Postgres, но и для полноценного HTTP-приложения, причём
"на каждое действие", а не только "на выдачу пропуска".

## 0. Тезис перед началом

"До сих пор мы видели два паттерна: Gateway спрашивает OPA на каждый
HTTP-запрос, а для прямого доступа к БД — OPA спрашивается один раз,
при выдаче credentials, дальше работает нативный механизм БД. Airflow —
третий случай: control-plane целиком HTTP, значит OPA можно (и нужно)
спрашивать на каждое действие — просмотр DAG, запуск, доступ к
Variables — совсем как в нашем собственном Gateway."

## 1. Alice (Company A, analyst) — видит только своё (2 минуты)

Откройте `http://192.144.13.138:8090`, войдите `alice` / `Password123!`.

Откройте вкладку **Dag-и**.

**Ожидаемо:** ровно один DAG — `company_a__load_dataset`.

**Тезис:** "Alice вошла собственным LDAP-паролем — не через Keycloak,
не через наш Gateway. Список DAG сформировала сама живая проверка
внутри Airflow: он спросил у LDAP, в каких Alice группах, и спросил у
того же самого OPA, что использует Gateway — можно ли ей видеть этот
DAG."

## 2. Carol (Company B, analyst) — контраст (2 минуты)

Разлогиньтесь, войдите `carol` / `Password123!`.

**Ожидаемо:** ровно один DAG — `company_b__load_dataset`, причём
**НЕ** `company_a__load_dataset`.

**Тезис:** "Тот же интерфейс, тот же код — но Carol физически не видит
даже название чужого DAG, не то что его содержимое. Изоляция не
'запрещено открывать', а 'не существует' с её точки зрения."

## 3. Dave (Company B, viewer) — отказ по роли (2 минуты)

Разлогиньтесь, войдите `dave` / `Password123!`.

Откройте вкладку **Dag-и** (не главную страницу — на ней у viewer
специально показывается `403` на виджетах статистики, это отдельная,
ожидаемая деталь UI Airflow, не связанная с нашей логикой).

**Ожидаемо:** `0 Dags`.

**Тезис:** "Dave состоит в компании B, как и Carol, но у него роль
viewer — по нашей матрице ролей viewer вообще не имеет доступа к
датасетам. Роль и tenant проверяются независимо друг от друга —
недостаточно быть 'из своей компании', нужна ещё и подходящая роль."

## 4. Живой код вместо магии — для инженерной аудитории (3 минуты)

Здесь стоит показать сам механизм, а не только результат — инженеры
обычно спрашивают "а как это работает под капотом".

Откройте `opa_auth_manager.py`, покажите `_fetch_ldap_groups` —
объясните, что это тот же самый `(member=<DN>)`-поиск, которым
пользуется `ldapsearch` в терминале, просто вызванный из Python.

Затем прогоните вживую:
```bash
docker exec demo-airflow python3 -c "
import ldap
conn = ldap.initialize('ldap://ldap:389')
conn.simple_bind_s('cn=admin,dc=demo,dc=local', 'AdminPass123!')
print(conn.search_s('ou=groups,dc=demo,dc=local', ldap.SCOPE_SUBTREE, '(member=uid=carol,ou=people,dc=demo,dc=local)', ['cn']))
"
```

**Тезис:** "Вот буквально то, что Airflow делает при каждом открытии
списка DAG — никакой магии, обычный LDAP-запрос, который мы все эти
недели делали руками."

## 5. OPA — общая точка решений для двух совершенно разных систем (2 минуты)

```bash
docker exec demo-opa opa test /policies -v | tail -10
```

**Тезис:** "Это тот же самый файл политики, `authz.rego`, который
обслуживает и наш собственный Gateway, и теперь Airflow. Мы не писали
вторую систему авторизации — просто добавили новый `resource.type` в
тот же словарь. Одна точка, где хранится 'кто что может' для всей
платформы, независимо от того, через какое приложение идёт запрос."

## 6. Честная оговорка (1 минута) — стоит проговорить, не скрывать

"Два момента, о которых стоит сказать прямо:

Во-первых, в отличие от Postgres, где у нас двойная защита — Gateway
и независимая RLS в самой базе — здесь вся изоляция держится на одном
компоненте, Auth Manager. Если в нём баг, второго независимого барьера
нет.

Во-вторых, решения OPA для Airflow пока не попадают в наш общий
аудит-лог в ClickHouse — только Gateway туда пишет. Это известное,
осознанное ограничение, а не забытая деталь — следующий логичный шаг
в развитии."

## Частые вопросы аудитории

**"Почему не Keycloak-логин, как везде?"** — можно, у Airflow есть
официальный provider под Keycloak (`apache-airflow-providers-keycloak`).
Мы выбрали LDAP напрямую, потому что это тот же паттерн "нативная
авторизация", что мы уже проверили на Postgres/ClickHouse, и он не
требует настройки OIDC redirect-флоу внутри ещё одного приложения.

**"А что если LDAP упадёт?"** — Alice не сможет залогиниться вообще
(fail-closed на аутентификации). Если LDAP упадёт уже ПОСЛЕ логина —
следующий вызов `_fetch_ldap_groups` вернёт пустой список (поймано
исключением), `tenant_id`/`roles` останутся пустыми, OPA откажет во
всём — тоже fail-closed, просто на уровне авторизации, а не логина.

**"Сколько времени заняла эта интеграция?"** — честно: дольше, чем
любая другая часть стенда, из-за нескольких малодокументированных
особенностей Airflow 3.x (dag-processor как отдельный компонент,
`get_authorized_dag_ids` вместо `filter_authorized_dag_ids`,
кэширование класса в уже запущенном процессе) — все три задокументированы
в `airflow-multitenancy.md`, чтобы не наступать на них повторно.
